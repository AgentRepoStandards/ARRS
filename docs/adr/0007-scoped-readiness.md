# Sourced scoped readiness preserves shared admission

Status: implemented; independent implementation review and human acceptance remain separate requirements under current R3 policy.

A repository maturity level cannot answer whether one concrete task has current matching proof or may be delegated under its effective scope risk. Readiness needs a bounded diagnostic projection while retaining existing work states, cumulative audit definitions, immutable evidence and protected policy admission.

The additive `readiness` schema uses version `0.1`. It is an output contract, not an input to work or proof admission. Dimensions preserve existing diagnostic statuses and expose reasons, source identities, prerequisites and remediation. Existing serialized work, proof and audit meanings are unchanged. Unknown versions fail through the existing schema registry.

`assessReadiness` composes preparation's pure work-item helper, shared policy requirements, explicit Git scope inspection, canonical proof explanation and shared work-state projections. It never persists those projections. Feature-only queries keep task eligibility unknown. Work queries retain selected proof diagnostics even when an unrelated proof cannot satisfy admission. Explicit scope/risk blockers may make advice stricter than the projected validator; the discrepancy is sourced and visible rather than silently reconciled by relaxing controls.

Preparation's path reader delegates to an additive pure `prepareWorkItem` helper with the same schema, size, source and non-executable-state checks. Public preparation behavior remains unchanged. Readiness supplies an ephemeral non-executable copy while evaluating the original item separately for shared state admission.

Read-only contextual audit executes no configured commands or external adapter runtime. Adapter coverage metadata stays contextual and its unsupported or unobserved qualification remains explicit. Static CI capability is distinct from hosted execution. Reader budgets are preflighted before shared validators so oversized observer input cannot trigger an unbounded fallback read. Observational limits cannot create acceptance.

No aggregate score, graph relation, maturity level, test count or lifecycle outcome authorizes execution or establishes semantic correctness. Required repository gates, R3 human stages, R4 exclusion, exact task/proof association and independent protected-baseline selection remain applicable.

# ADR 0007: Offline trusted receipt provider and consumer

Status: accepted design for offline conformance; real hosted receipt qualification remains pending separate authorization and evidence. Hosted CI was manually disabled during the original implementation; enabling the repository's public launch workflow does not qualify hosted receipts or provider admission.

## Problem and decision

Local proof verifies source freshness, commands, scenario links and immutable attempts. Its hashes and local review text cannot authenticate a machine or a person. Keep all existing local proof, retained policy, alias and review behavior. Add a separate opt-in version 1 receipt contract and a read-only consumer. Unsupported versions, providers, algorithms and payload types fail closed.

Use an in-toto Statement v1 (`https://in-toto.io/Statement/v1`) with predicate `https://arrs.dev/predicates/trusted-receipt/v1`, carried by a DSSE envelope. The bounded profile uses one Ed25519 signature over DSSE PAE and canonical compact sorted-key JSON, canonical base64 and strict schemas. Node's standard `crypto` implements signing verification; no package, credential, signing CLI or network dependency is added. This profile is intentionally narrower than generic in-toto/DSSE, and does not claim compatibility with every artifact attestation, SLSA certification or semantic adequacy of tests. A future GitHub artifact attestation adapter must negotiate a new provider/profile and qualify its real issuance/verification surface; it cannot silently reinterpret this offline version.

## Selected authority and responsibilities

The external consumer selects two files, outside candidate source, and pins their raw SHA-256 independently: policy and expected request context. Paths are absolute, nonsymlinked, singly linked and bounded. Neither a receipt nor candidate configuration discovers its own trust roots. A file path, digest or timestamp alone cannot authenticate who selected it; the caller must establish that provenance through its protected system before using this API.

Policy selects three distinct Ed25519 keys/key IDs: verifier, provider observation authority and protected review authority. It pins verifier ID, workflow repository/path/immutable revision, tool digest, allowed trigger forms, opaque approved reviewer IDs and maximum lifetime. These fixture authorities simulate independently protected inputs, not real GitHub production identities. The verifier must obtain actual executed command/log observations, complete Git comparison and canonical technical validation; signing arbitrary candidate assertions is ineligible. The provider authority authenticates run/artifact observations. The review authority authenticates protected review events. Merely signing local independent/humanApproval strings supplies none of those observations.

Expected context selects repository, full immutable candidate revision, explicit comparison base, exact proof attempt/manifest digest, Git scope fingerprint, required command argv digests/timeouts, criterion digests and challenge. It retains governing control identity/digest, required gates and review requirements selected independently before candidate creation. The signed event order must be `controls.selectionSequence < candidateSequence <= evaluationSequence`, and candidateSequence must match the externally selected request. Event sequences are protected provider assertions, not local wall-clock evidence. The consumer must compare these against actual protected selection/candidate events; an author assigning favorable numbers does not establish history. Baseline/candidate maximum gates and mapped targets remain the external verifier's responsibility, with retained source controls and original command bindings checked by existing local proof before export. A comparison base is never a policy baseline.

The consumer compares signed observations against its independently expected requirements. Required checks cannot be skipped, omitted or replaced with different argv/timeout digests. Every acceptance criterion must link to a successful executed behavioral result (mechanical success alone cannot cover feature behavior). Before/after command bindings remain identical. Immutable subject and complete Git scope identify the candidate/base; declared-only local exports remain useful engineering evidence and cannot satisfy this provider profile.

## GitHub offline adapter

The adapter projects bounded GitHub run fields (`id`, repository URL, `head_sha`, `event`, `status`, `conclusion`, created/updated instants), artifact name/size/`sha256:` digest and review fields (`id`, `user.id`, `commit_id`, `state`, `submitted_at`). Workflow/tool/control identities and observed commands come from the protected fixture authority, not candidate workflow text. Exactly one metadata-only `bundle.json` artifact is supported. The conformance harness runs an actual public CLI proof over a committed candidate, exports shared-validator metadata, derives the run projection and signs run/review/receipt observations with ephemeral test keys.

Supported triggers: explicitly policy-selected `pull_request` and `workflow_dispatch`. `push`, `pull_request_target`, skipped/unknown execution and unsupported forms cannot supply protected acceptance. Review forms are `APPROVED`, `CHANGES_REQUESTED`, `DISMISSED` with opaque GitHub numeric IDs. The highest protected sequence for each required role is authoritative; duplicates reject, later revocation overrides approval. Roles are separately protected assertions, since ordinary GitHub review alone does not distinguish final human acceptance from independent technical review. The authority must collect the completed exact revision/attempt after execution, and map roles under external organization policy. Candidate author/verifier cannot approve their own work. Local author names and approval prose are not adapter inputs. API pagination, deleted accounts, organization membership, merge queue, reruns and actual hosted identity extraction are unqualified and unsupported by this offline profile.

## Freshness, reuse and output

Policy/request define a bounded UTC lifetime and one externally issued challenge. Repository/revision/base/run/attempt/manifest/controls/review bindings must agree. Reused consumed challenge or receipt digest rejects in admission mode. Explicit inspection mode can reuse it only when policy allows; inspection is never readmission. This verifier is read-only and does not update replay state. A real consumer must atomically validate/consume external challenge and receipt digest before actual admission, using a current independently generated request time. Concurrent state updates, clock trust and atomic admission are responsibilities of that future protected consumer.

Results separately report authenticity, freshness, policy, scope, evidence and acceptance. All must pass for `valid`/`conformancePassed`. Every result retains `assurance: offline-provider-conformance`, `hostedAssurance: not-qualified`, `admission: false`. Protected fixture review conformance is not actual human acceptance of the ARRS implementation. Production admission remains disabled for this profile even when signatures and fixtures pass.

Local export reuses shared canonical technical validators and preserves original proof/session/log/review bytes. It exports digests, opaque IDs and ordered result links, omitting source/log contents, argv, criteria prose, review names, external paths and credentials. `acceptedLocal` is informational local review state, never provider authenticity. Git exports require committed source layers; non-Git/legacy exports retain declared-only assurance. Import revalidates signed provider digests before exclusive writes into a new ignored contained directory outside canonical evidence. Files are bounded to 1 MB, outputs preserve existing directories and use private creation modes. Metadata can still be sensitive, and cannot be certified secret-free merely by a schema; inspect before deliberately sharing. No command uploads or executes GitHub workflows.

## Residual attacks and qualification

Selected authorities can lie or be compromised; algorithms do not make poor tests meaningful. External trust/request selection can be wrong, verifier software can be malicious, and protected reviewer account access can be stolen. A file-based observation can change concurrently; import rereads/rechecks its copied bytes, while real execution needs a separately qualified immutable acquisition boundary. Key rotation/revocation, transparency, OIDC certificate chains and real provider issuance are deferred to an explicitly authorized hosted slice. Do not enable hosted receipt issuance or change branch protection as offline receipt setup. Record exact provider/workflow/revision and actual execution permission in that later qualification. No new receipt upgrades old local proof or supplies the independent/human implementation gates required by this repository.

# 0006: Versioned bounded adapters and provisional Python

Status: candidate implementation direction; real-pilot selection and implementation acceptance pending.

ARRS currently enforces JS/TS literal module boundaries. Issue #40 requires the first additional language to be selected from a real pilot and its actual package/import inventory. The user reports that this inventory is unavailable. Reversible candidate implementation can be prepared, but neither synthetic fixtures nor an available Python interpreter establish that selection or application qualification.

Keep the existing architecture policy version `0.1` and add optional adapter selection with a separate tested contract version. Absent selection preserves `javascript-typescript@js-ts-0.1`. This is an additive schema change: older CLIs reject the new field and must not be used for selected-adapter policies. Unknown IDs/versions fail visibly; no dynamic plugin ABI or external adapter installation is defined.

The opt-in candidate is `python@candidate-python-ast-0.1`. It uses a single configured literal interpreter executable and isolated stdlib `ast.parse`, passing bounded source through stdin. It never imports/executes application modules. Its package roots are explicit search directories, ordinary packages have `__init__.py`, and all activated local package initializers must satisfy declared ownership, dependency direction and public interfaces. Literal `import` and `from` forms resolve to safe repository files; relative levels cannot escape their package root. Same-module imports are permitted; cross-module imports must follow allowed direction and declared public files/directories. Each activated package initializer is an actual resolved import target and receives the same ownership, dependency-direction and public-interface checks as the named file. Dynamic/custom loaders, recognized resolver modification, namespace packages and ambiguous roots fail unsupported. Named imports are linked to files; the checker does not prove that a requested symbol exists at runtime.

Keep source discovery, safe paths, most-specific generated ownership and the forbidden-edge guard in shared architecture core. The selected analyzer parses both ordinary source and an in-memory injected forbidden import. The guard does not modify the worktree. Ignore no known unsupported language source in declared handwritten scopes; reject mixed known source languages and disclose non-source/unknown files in reports. Explicit generated modules remain excluded, and separately declared handwritten descendants remain scanned even under `build`, `vendor` or `dist`.

Read-only doctor and unexecuted audit never launch a configured external parser: they disclose Python source inventory with zero analyzed files and `not-evaluated` architecture, with guard blocked. The shared coverage/check API supports `allowExternalRuntime: false` for readiness/MCP/report consumers. Explicit gate and executed audit can analyze a trusted selected runtime. A diagnostic reports adapter/contract identity, declared scope, discovered and successfully parsed file counts, unscanned files, errors, provisional qualification and (for audit) the actual guard result. A missing/failing/timed-out/parser, malformed/partial output, zero source or unsupported result cannot pass capability. Parser diagnostics do not expose application contents or run native acceptance commands. The configured interpreter is trusted local code like other literal repository commands; these controls do not authenticate it or establish a hostile-runtime attestation.

Python's provisional label remains visible in doctor/audit and documentation. Synthetic consumer tests run a real permitted import and a rejected forbidden import through configured commands, with actual proof freshness, but are controls testing only. Complete actual source inventory, approved runtime/paths and permitted/forbidden pilot evidence before selecting/finalizing the additional-language subset for #40. Revising that subset or contract requires its own reviewed version and conformance.

No new npm dependency is added. Candidate testing uses the environment's existing Python 3.12.14; consumers supply their own explicitly configured Python 3 runtime. Hosted CI was manually disabled during candidate development. Passing local conformance does not change CI settings, qualify a real application pilot or grant extra autonomy; the public launch workflow is separate.

# Local capability graph and explicit provenance

Status: implementation decision; completed implementation acceptance remains separate.

The graph is a read-only projection of maintained Feature Maps, configured targets, document references and explicitly selected work/proof records. It does not infer runtime dependency reachability or semantic prose freshness from path names. A path overlap reports every applicable map and retains all risk/target obligations; an unsupported language or computed import remains an analysis gap.

The result has its own versioned `capability-graph` contract. Node identity uses a kind plus maintained feature ID or normalized repository path. v0.1 invariant and acceptance strings have no author-supplied stable IDs: their node IDs are content addressed by feature ID and exact text. Reordering text preserves identity; editing text changes identity. This is textual identity, not stable semantic identity. Existing Feature Maps remain unchanged. A future explicit-ID contract needs migration rather than silently assigning new authoritative IDs to old maps.

Every edge names origin (`maintained`, `observed`, or `candidate`) and source path, JSON pointer, content digest and optional comparison revision. Maintained references and observed validated evidence remain separate. Candidate associations never grant readiness. The graph identity covers configuration, maps, policy, declared reference state and selected work/proof/review records; it contains no generated timestamp.

`impact --base <local revision>` consumes the complete explicit changeset API, preserving added/deleted/renamed/unmapped endpoints and historical floors. Source queries use declared paths and label their discovery limit. `context feature <id>` returns that capability's maintained statements, configured targets, decisions and explicitly related work/evidence. `context drift --base <revision>` compares contract facts and references with before/after provenance. Removed targets/paths and changed invariant/acceptance text are factual drift; code changes alone do not establish semantic staleness.

Evidence qualification reuses readiness and the shared technical/accepted proof validators. Only a work item's exact selected canonical attempt can qualify that work's criteria, and only explicitly declared feature membership plus matching criterion text connects that evidence to a feature statement. Unrelated proof is never credited from shared filenames, target names or criterion coincidences. Current technical/unreviewed, accepted, stale, failed, missing and unknown evidence remain distinct. Feature suitability without a concrete task remains unknown.

Generation has bounded maps, metadata, nodes/edges and output pages. Duplicate IDs, unknown versions, dependency cycles, unsafe/symlink paths and malformed contracts yield diagnostics and an incomplete result, never partial success. No database, model dependency or cache is introduced. JSON, terminal and local HTML rendering consume the same result; default queries perform no writes or repository command execution. Explicit Git inspection invokes only the qualified read-only Git adapter. Human execution authorization, protected baseline selection, independent review and final acceptance remain separate controls.

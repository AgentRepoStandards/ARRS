# Guided adoption uses explicit facts and exact-byte proposals

Status: implemented; independent implementation review and human acceptance remain separate from execution authorization.

Adoption is an authoring operation for one existing capability. `adoption-input`, `adoption-proposal` and `adoption-authorization` are distinct strict version 0.1 documents. Existing configuration, architecture, risk and Feature Map 0.1 meanings remain unchanged. Older CLIs reject the new schema kinds; no migration or new unknown fields are added to existing contracts.

Planning supplies provenance for existing manifests, configured commands, package scripts and scoped instructions. Those candidates never replace owner-supplied acceptance, declared modules, actual paths or explicit verification bindings. Missing/unsupported facts produce ordered blockers. Partial proposals can be reviewed and exported but cannot be applied. Plans have no timestamps, random IDs or root-dependent output metadata; identical input and snapshot bytes produce identical operations/checklist/blockers. Export also writes a readable whole-file `patch.diff` preview; it is not an executable patch. Export adds only output artifact paths and SHA-256 to the command result, outside the proposal document.

The proposal embeds input, its source path, snapshot digests/modes and exact original/replacement bytes. Array/object integration only appends explicit modules, sensitive-path rules or one verification target. Token-aware insertion preserves every unrelated existing byte, newline convention and file mode; duplicates/conflicts require a separately reviewed change. Existing maps, root instructions, sources, ignore rules and lockfiles are never overwritten. Existing check/test/build/verify mappings and a valid starting contract are prerequisites for application; unconfigured initialization still receives an honest partial plan. The workflow does not infer architectural constraints or approve dependencies.

Apply validates the strict proposal, every safe source/destination, duplicate targets, original bytes/modes, input snapshots and deterministic regeneration before effects. Existing governing-control edits require independently supplied known-good pre-change baseline context and a separate actual execution-authorization record bound to the proposal's raw SHA-256. Proposal-authored rules and approval-looking fields cannot relax the existing gates. The current/baseline risk classifier applies; R4 stays human-owned. Authorization text is a local assertion with the same trust limit as proof authorization, not authenticated identity or completed implementation approval.

Output/recovery uses canonical fresh `.arrs/adoption/<name>` directories with the existing whole-directory ignore protection contract, outside proof evidence. Retained recovery originals include bytes, modes, expected replacements, applied paths and status. Apply writes a prepared journal before mutations, writes new files exclusively, stages existing-file replacements in recovery and renames them, records each attempted path before mutation, then updates the journal after each successful write. A prefix written before a failed new-file write remains an explicit partial-write diagnostic with retained original absence. Ordinary failures roll back already applied files only while bytes/modes still match the proposal replacement. Changed intervening work remains intact and produces `partial-write` with explicit rollback errors. Created empty source parents are removed on rollback. Originals remain reviewable after successful or failed application.

This is a cooperative local operation, not a cross-process transaction: interruption can occur between replacement and journal update. After a crash inspect every operation and compare actual bytes with both retained expected/replacement digests; restore originals only after reviewing intervening work. A prepared journal contains the originals even if its applied list is incomplete. There is no automatic recovery command that could overwrite such work. Reapplying rejects stale input and never overwrites a previous application. No application scripts, installs, network requests or commands execute during planning/apply; ignored-storage probes use bounded local Git inspection.

Successful application reports `configured`, `behavioralProof: "not-evaluated"`, `accepted: false`, changed paths, recovery and remaining checks. Existing doctor/audit/proof behavior remains authoritative. Configuring a map does not create executed verification, dependency acceptance, hosted CI observation or maturity promotion. Hosted CI was disabled under the maintainer's instruction during development. Adoption does not change CI settings; the public launch workflow is a separate maintainer-controlled step.

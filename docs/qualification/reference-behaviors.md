# Observable reference Feature Map behavior

The five [reference Feature Maps](../features/README.md) remain capability-sized. Their acceptance criteria name command-boundary results rather than repeating their goals. The table links each configured target to actual scenarios; run the target and inspect its output/proof to establish execution. A linked test name alone is a source pointer, not captured evidence.

| Map and configured command              | Observable scenarios and source pointers                                                                                                                                                                                                                                                                                                                                                                                                 | Limits                                                                                                                                                                       |
| --------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Bootstrap — `./repo verify bootstrap`   | [CLI tests](../../tests/cli.test.mjs): “CLI initializes empty repository with actionable commands and idempotent preservation”; “dry run changes nothing and existing conventions/instructions are byte preserved”; “initialized architecture is valid incomplete setup and cannot qualify Level 2”; “standard runner retains exit status and argument values without shell evaluation”; timeout/output/owned-group cleanup cases        | Presence and generated mappings do not establish app adoption, command trust or human approval                                                                               |
| Audit — `./repo verify audit`           | [Diagnostics](../../tests/diagnostics.test.mjs): read-only nonexecution, unconfigured prerequisites, broken references and command failure; [core](../../tests/core.test.mjs): canonical imports versus forbidden/private/unresolved/computed imports, guarded source discovery and unsupported loaders; [audit](../../tests/audit.test.mjs): cumulative classification, pending-review rejection and protected context before execution | Instruction/CI inspection is bounded static syntax/presence; no hosted run, branch protection, semantic domain correctness or universal language coverage                    |
| Proof — `./repo verify proof`           | [Proof tests](../../tests/proof.test.mjs): real feature output and freshness; required failure propagation; failing-before/successful-after bug; preserved refactor scenario; immutable finish/retries; actual selected-review binding and noncanonical rejection                                                                                                                                                                        | Local hashes/logs are integrity checks, not authenticated execution; the current scope can still omit undeclared changed files unless an explicit changeset contract is used |
| Skills — `./repo verify skills`         | [Skills tests](../../tests/skills.test.mjs): offline idempotent install, byte preservation, staged source/supporting references, malformed inventories and exact license rejection, shared doctor/audit validator                                                                                                                                                                                                                        | Contract/provenance checks do not measure semantic skill quality or establish application benefit                                                                            |
| Operations — `./repo verify operations` | [Workflow tests](../../tests/workflows.test.mjs): sensitive-feature floors and unsafe context, unsupported providers, selected retry and completed-review gate, local metrics/Gardener; “pilot protocol preserves unknown denominators, exclusions and deterministic local replay”; malformed/unsafe ledger preservation; actual failed/selected proof binding                                                                           | Self-reported observations remain fallible; synthetic ledger replay establishes collection behavior, not recruited pilots, timing, savings, defect absence or autonomy       |

Each map retains its owning modules, real entry/implementation paths, existing verification target and risk floor. Additive scenario pointers live in `related`; they do not change the shipped Feature Map schema or existing literal target argv. A map's `acceptance` is a desired behavior; map validation checks its structure, references and target rather than proving that prose is semantically correct. [Knowledge scanning](../feature-maps.md), [security heuristics](../security.md) and [bounded CI inspection](../spec/0.1.md) retain those explicit limits.

The [controls walkthrough](pilots/walkthrough.md) runs actual configured acceptance and negative scenarios, failed/revised proof and separately bound review in disposable synthetic repositories. The [pilot protocol](pilots/README.md) specifies what must be collected from actual authorized application work before making engineering-outcome claims. These local scenarios do not require hosted CI and do not evaluate hosted runs. Enabling the public launch workflow is separate from this local evaluation.

# Real application evaluation protocol — pilot-0.1

The evaluation asks whether adopting one ARRS capability reduces maintainer effort for a bounded task without concealing rejection, retries, reverts or defects. Three actual applications are required: established; smaller/newer; legacy or another language. Recruitment is **outstanding** in all three contexts. The [missing-observation fixture](missing-observations.json) tests bookkeeping with invented values; it is not application evidence. Existing [v0.1 qualification](../v0.1.md) and the [controls walkthrough](walkthrough.md) are synthetic controls testing.

An evaluator recruits maintainers with permission for the specific application, paths, commands, installation and observation retention. Keep the actual repository name, source/import inventory, permission record and alias-to-participant mapping in a private ignored `.arrs/pilots/` inventory outside public source. Give each pilot a stable pseudonymous identifier. Record authorized scope and prohibited actions before selecting tasks; a repository URL or access credential is not execution authorization. Do not change production data or hosted application CI for this evaluation. Application CI is `manual-disabled` or `not-evaluated`; local completion does not imply hosted admission. Enabling ARRS's public launch workflow does not change application evaluation permissions.

The initial target is roughly 30 tasks distributed across feature, bug, refactor and documentation work and all three applications. This is a sampling target, not a safety threshold. Select consecutive eligible tasks when feasible and retain excluded candidates with an exclusion reason. A task is eligible when its maintainer defines a bounded objective, category, risk, explicit scope, observable acceptance scenario and authorized commands. Exclude unavailable access, prohibited production work, unbounded changes, tasks with no authorized reviewer and unsupported mechanisms that cannot be mechanically verified. Describe selection bias and category/risk imbalance in the findings; do not fill an empty cell with an invented task.

Assign a stable task identifier before execution, retaining it across revisions. Record separate attempt identities and immutable proof paths; retries are not independent samples. Retain unsuccessful/interrupted attempts, selected proof, task/work identity, workflow/tool aliases and the selection reason. Record every scoped authorization and governing controls revision in the private inventory. Study observations supplement the actual application policy, Proof Contract and review; they grant no permission or acceptance.

Before a run, freeze the planned collection window and comparability criteria. The default follow-up is 14 calendar days after accepted completion; use a different predeclared window where the application requires it and disclose it. Record its UTC start/end privately, completed days and whether final follow-up is complete. Final revert and escaped-defect values remain `null` until the planned window completes; interim signals belong in dated observation records and findings, not a premature final zero. A missing review is unknown even when verification passed. A completed window alone does not make its observations known.

| Measurement                | Unit and collection point                                                                                                                                                                                            | Unknown handling                                                                    |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| Adoption/setup effort      | Active human seconds mapping the existing commands, reviewing the capability patch and configuring it; collect once per application/capability before the first task, then allocate explicitly if comparing per task | `null` if not timed; never count it once per task accidentally                      |
| Context interventions      | Count of explicit human corrections or missing-context answers from prepared handoff through selected passing proof                                                                                                  | `null` if no observer; zero requires affirmative observation                        |
| First-pass verification    | Boolean for the first full planned verification attempt after implementation; record its attempt identity                                                                                                            | `null` for missing attempt/results; passing unit tests alone do not satisfy it      |
| Verification retries       | Count of subsequent actual attempts for the same original task, including failures                                                                                                                                   | `null` if attempt history is incomplete                                             |
| Active review effort       | Human seconds actively inspecting the actual diff and selected evidence until review decision, with separate subsequent revision review times                                                                        | `null` if not timed; waiting time is excluded                                       |
| Review rejection           | Boolean from the actual selected implementation review, with separately linked revision attempts                                                                                                                     | `null` when review is missing/pending                                               |
| Revert and escaped defects | Boolean revert and nonnegative defect count from explicit observation over the completed follow-up window                                                                                                            | `null` until final follow-up and observation are complete; a zero is an observation |
| Elapsed task duration      | Wall-clock seconds from task handoff to selected accepted completion; pause/wait and intervention intervals are disclosed privately                                                                                  | `null` before completion; never substitute elapsed duration for human effort        |

Use feasible baseline work from comparable historical or prospectively observed tasks under the same application, category, risk, scope size and observation window; changing maintainer, tools, task difficulty or adoption familiarity is a confounder. Avoid executing an identical fixed task twice and treating the second run's learned context as an unbiased comparison. If no defensible baseline exists, report assisted descriptive observations and exclude that comparison with a reason. Counterbalance order when possible. Separate setup cost, task effort and review effort; report elapsed waiting separately. Report every metric's observed/missing denominator, eligible/excluded count and pilot context. A small self-selected sample supports descriptive findings, not causal savings, model rankings or autonomy increases.

## Local opt-in checklist and replay

The repository-local checker reads a ledger and existing canonical proof metadata. It runs no application commands, writes no observations and sends nothing over the network. Build the checkout first. No dependency or protected command binding is added:

```sh
./repo build
node scripts/pilot-protocol.mjs docs/qualification/pilots/missing-observations.json
node scripts/pilot-protocol.mjs .arrs/pilots/ledger.json
```

`pilot-0.1` is this evaluator's ledger format, not a new ARRS configuration/schema version. Start from the fixture shape with `kind: "application-study"`, actual private inventory references and actual observations. The checker refuses application observations for a pilot whose recruitment is outstanding. IDs, categories and coded confounders are bounded; arbitrary notes, source/customer contents, secrets and review transcripts are not admitted fields. Paths are local references checked through the shared safe-path implementation; report output omits scope and task paths. `metricsReferences` link local observation identities without copying their contents. Keep substantive selection rationales and additional confounder explanations privately under their coded references.

Prefer the existing `metrics` and `proof` interfaces for capture. The original v0.1 metrics event requires complete outcomes; do not fabricate booleans/zeros to fit it. The #37 `metrics observe` interface, when available, accepts nullable/absent observations and keeps revisions separate; use `activeSeconds` and `durationSeconds` for human effort and elapsed duration, with setup/review breakdown in this protocol ledger. Link its observation IDs in `metricsReferences`. Neither metrics nor this ledger automatically reconciles work completion.

For each task: review capability adoption patch; prepare its bounded context and draft proof; classify with its actual policy; authorize configured command execution; run an actual negative acceptance scenario; execute and validate actual proof; inspect each failed/revised attempt; obtain separate implementation review of the selected passing attempt; record accepted completion only when the required proof/work gates admit it; then observe the declared follow-up. Use #32 adoption, #33 preparation and #35 reviewer reporting when those interfaces are available. The [walkthrough](walkthrough.md) demonstrates those control boundaries without claiming a recruited application.

Every `attempts` entry must be a canonical local proof manifest and match task/category/risk/scope; `selectedAttempt` must be one of the retained entries. Existing shared technical and accepted validators establish freshness and bound review. Failed/stale/unreviewed attempts remain visibly invalid/pending; they do not turn observations into completion. For protected evidence, supply the independently retained context through `--baseline <directory> --baseline-sha256 <digest>`; the ledger cannot select its own trusted baseline. The report includes manifest digest, attempt identity, captured status, current validation state and executed command keys/status/duration without logs, argv or raw source. Boundaries remain local cooperative evidence, not signed attestation.

Malformed/oversized records, duplicate IDs, unknown versions/fields, unsafe paths and noncanonical/mismatched attempts exit nonzero. Underlying command failures remain in the proof's command statuses and technical state; reading a failed attempt is permitted to retain failure history and never awards acceptance. Earlier observations and proofs are never modified. Replaying identical bytes against unchanged proof/source/control state is deterministic; freshness changes deliberately change evidence validation.

An explicitly requested local export previews exactly the sanitized report on stdout:

```sh
node scripts/pilot-protocol.mjs .arrs/pilots/ledger.json --export
```

Review the displayed report before choosing a local destination or sharing it. There is no automatic network send. Counts/measurement values and pseudonymous IDs can still be sensitive: the evaluator controls access, retention and disclosure, and destroys alias inventories according to participants' agreed retention. Do not publish raw application proof, participant permissions or application source.

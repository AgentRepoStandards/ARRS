# ARRS specification v0.1

Status: implemented v0.1 contract. Specification and serialized contract version: `0.1`. CLI package release: `0.1.0`.

**MUST** is required for conformance; **SHOULD** is the default with a documented reason for deviation; **MAY** is optional. Requirements describe both repository practice and the reference tool. The audit matrix below defines exactly what the reference CLI measures; policy obligations beyond those checks still require judgement.

## 1. Repository contract and context

An ARRS repository MUST keep its engineering contract in repository files. A ready work item MUST be executable without hidden conversation memory. Root `AGENTS.md` MUST provide a concise operating contract and conditional pointers; it MUST NOT require every document to be loaded for every edit. Scoped instructions MAY describe genuinely different areas.

The durable contract MUST identify project commands, architecture, decisions, product/domain knowledge, Feature Maps, risk, proof, skills and CI. Substantial multi-step or context-spanning work SHOULD maintain an execution plan with objective, constraints, decisions, milestones, state, discoveries, verification and completion evidence. Trivial R0/R1 changes MAY omit a separate plan.

Repository practice MUST preserve required tests, static checks and behavioural verification. A failing implementation MUST NOT be made acceptable solely by weakening its controls. Repeated preventable failures SHOULD result in stronger types, architecture, checks or tests before additional instructions.

## 2. Versioned configuration and commands

The reference configuration is `arrs.json` validated against `schemas/config.schema.json`. Configuration, Feature Maps, architecture, risk, proof plans/manifests/review records, exceptions, metrics and work items MUST declare `schemaVersion: "0.1"`. Their schema identifiers include `/schemas/0.1/`; these identifiers are names, not a runtime network dependency. Unsupported versions and extra properties MUST fail validation.

Configuration MUST declare `project`, `commands`, `verifyTargets`, `knowledge`, `architecture`, `riskPolicy`, `proof`, `skills`, `ci` and `security`. The schemas define their field structure. Incomplete command mappings MAY exist during adoption but MUST be reported as incomplete capability. Optional `work` selects `provider` and safe repository-relative `path`; absence preserves the local `.agent/work-items` implementation. Unsupported providers MUST remain unproven and fail work operations.

The standard interface is `./repo setup`, `dev`, `check`, `test`, `verify [target]` and `build`, backed by `arrs run`. Each configured command MUST contain a nonempty `argv` array and MAY set `timeoutSeconds`. Commands MUST run from the repository root with `shell: false`; argument strings MUST retain literal argument semantics. Missing commands/targets, spawn failures and timeouts MUST fail explicitly. The command interface MUST preserve executed exit status. A configured shell/interpreter remains an explicit trusted executable.

Timeout, output-limit termination and cancellation MUST retain ownership through bounded cleanup of the original command group/tree, including descendants with independent stdio that outlive the direct child. A leader closing MUST NOT cancel required escalation. First termination cause and cancellation signal MUST retain their exit semantics; repeated interrupts MUST NOT restart cleanup. Windows termination helpers MUST be observed before cancellation completion. Descendants deliberately detached into other groups, SIGKILL of the caller and abrupt machine loss remain outside cleanup guarantees.

Repository references MUST be relative paths using `/`; absolute paths, traversal and unsupported symlink paths MUST be rejected. Generated evidence MUST be strictly below the normalized repository-root `.arrs/` directory, default `.arrs/evidence/`. Before capture commands/allocation and log/session/manifest/review writes, whole-directory exclusion MUST be established; current evidence validation MUST recheck protection. In a Git worktree (including a containing worktree), bounded shell-free `git check-ignore --no-index --quiet -- <normalized-directory>` without a trailing slash MUST exit zero for the existing evidence directory or an existing ancestor. An absent destination MUST NOT be treated as a verified directory: without an ignored existing ancestor, canonical scoped protection is required even with Git available. Operational Git failure MUST fail closed. Without Git/a worktree, or for a prospective directory without an ignored existing ancestor, only canonical scoped wildcard protection (`*` or `/*`, optional `!.gitignore`, empty lines and first-column comments) MAY qualify as a bounded local convention; other patterns/negations/indentation MUST be rejected. Capture/review output MUST identify the method and disclose that fallback does not measure Git state. Ignore rules do not untrack existing files or establish secrecy.

Global CLI option applicability MUST be validated before filesystem mutation, command execution or network dispatch. `--root` and `--json` apply universally; `--dry-run` only to init; `--execute` only to audit and proof run/start/finish; `--require-level` only to audit; `--risk` to risk and metrics summary; metrics filter flags only to metrics summary and --preview only to metrics export; `--to` only to work transition; `--accepted` only to proof validate. Unsupported action flags MUST fail nonzero with an actionable error, including valid JSON with `--json`. Presence MUST be checked even for values such as level 0 and risk R0. Skills-specific options retain their action validation. Help/version behavior is read-only.

Dotenv text security coverage MUST include root and nested `.env` files with nonempty dot suffixes, including `.env.local`, `.env.production` and compound variants. Existing supported source extensions, the 2 MB file bound, safe-path rules and deliberate diagnostic generated-directory exclusions remain unchanged. Findings remain heuristic; secrets MUST NOT be waived.

## 3. Initialization and doctor

`arrs init [directory]` MUST work in new and existing repositories, preserve existing files and report created/preserved paths and actionable requirements. It MUST detect existing instructions and supported command conventions without fabricating product facts. `--dry-run` MUST report planned changes without writes. Repeating initialization MUST preserve prior content. A missing `.arrs/.gitignore` MUST be generated regardless of literal root ignore lines; root and scoped user files MUST remain untouched. Existing unsafe protection MUST be reported with remediation. Initialization MUST remain functional without Git.

`arrs doctor` MUST assess configuration, executable/runtime availability, reference integrity, Feature Maps, risk/proof prerequisites and installed skills. It MUST report actionable problems rather than silently invent commands. Doctor is diagnostic; it does not itself demonstrate successful acceptance behaviour.

## 4. Feature Maps

Feature Maps MUST be JSON under `knowledge.features`, validated by `schemas/feature.schema.json`. They MUST identify goal, owners, entry points, implementation, boundaries, dependencies, domain terms, invariants, sensitivity, acceptance, verification target, baseline risk and related context. Every referenced implementation/documentation path MUST be real, and verification MUST name a configured target.

Configured verification targets MUST be explicitly owned entries in `verifyTargets`. Feature Map validation, work readiness and both command runners MUST reject absent inherited object names as unconfigured targets. Deliberately configured own names allowed by the existing schema MUST retain literal argv execution and exit-status propagation.

Maps SHOULD cover meaningful user/system capabilities rather than every helper. Changes affecting a map's behaviour or boundary MUST maintain its contract in the same change. Validation detects structural and path staleness; semantic freshness still requires implementation and acceptance review.

## 5. Mechanical constraints

Architecture policy MUST declare real module paths, allowed module dependencies and public interfaces. The reference JavaScript/TypeScript adapter MUST reject checked relative imports that violate ownership, dependency direction or public interfaces. It MUST fail on unresolved local or computed imports and unsupported detected repository aliases. Generated exclusions MUST be explicit. A constraint claim MUST include an actual scan and a negative mutation guard using the same scanner.

Declared-source discovery MUST NOT exclude handwritten files merely because a directory is named `build`, `vendor`, `dist` or another diagnostic discovery default. The most-specific normalized architecture module path determines ownership and its `generated` exclusion; handwritten descendants of generated parents MUST remain checked when independently declared. Scanner and mutation-guard candidates MUST use the same discovery contract.

During adoption, `modules: []` is a schema-valid unconfigured scaffold, not an architectural capability. Both scan and guard MUST reject that incomplete state with configuration guidance; malformed configured entries MUST still fail validation.

The adapter does not cover every language or runtime dependency mechanism. Repositories SHOULD use their stack's mechanical gate for unsupported mechanisms and document scope. v0.1 has no dynamic plugin ABI.

Architecture policy MAY select a versioned `adapter`; absence MUST retain `javascript-typescript@js-ts-0.1`. Unknown adapter IDs/versions MUST fail unsupported before analysis. The opt-in `python@candidate-python-ast-0.1` contract is provisional and MUST NOT be represented as selected/qualified by a real pilot without actual inventory and application evidence. It MUST use explicit safe package roots, isolated nonexecuting stdlib AST analysis, literal bounded runtime argv and the same analyzer for ordinary/forbidden-edge scans. Read-only diagnostic consumers MUST NOT execute configured external parser runtimes; unavailable analysis MUST remain not-evaluated/blocked with zero analyzed coverage. Missing/failing/timed-out runtimes, malformed/partial output, unsupported loading/package mechanisms and zero coverage MUST NOT pass capability. Shared most-specific ownership/public/direction and generated-source rules remain active. Mixed known unsupported source MUST fail, and other unscanned files MUST be disclosed. Diagnostic reports MUST identify adapter/version, provisional limits, discovered/successfully parsed source counts, scope and actual guard state. This additive policy field retains version `0.1`; older CLIs reject it. See the [bounded contract](../architecture/adapter-conformance.md).

Security controls MUST make detected secrets, unsafe remote-execution shortcuts, suppressions and unjustified dependencies visible. Scoped exceptions MUST record path, rule, matching text, reason, expiry and approver; secret findings MUST NOT be excepted by this mechanism. Dependency declarations MUST have justification records where the security gate requires them. This heuristic scan is not complete security analysis.

## 6. Proof and verification

Every completed work item MUST satisfy the applicable Proof Contract and risk-required checks. A proof plan MUST record task, category, risk, scope, acceptance, ordered command steps, residual risks and deviations. A proof manifest MUST additionally record actual commands, expected/actual exits, durations, evidence references/digests, timestamp, status and current scope hashes.

- **Bug:** MUST retain a failing pre-change reproduction and successful post-change result for the same scenario.
- **Feature:** MUST record successful behavioural evidence covering acceptance criteria.
- **Refactor:** MUST demonstrate equivalent successful behaviour before and after.
- **Docs/mechanical:** MUST use proportionate checks; purely textual work MAY omit runtime behaviour.

Required checks MUST exit zero. An expected failure is permitted only for an appropriate baseline reproduction and MUST NOT conceal failure of a required check. Technical proof MUST fail if required checks, criteria, configured risk/execution-authorization gates or evidence integrity fail. Accepted proof MUST additionally enforce current policy-required implementation review. Scope changes MUST invalidate stale hashes. An incomplete/failed command MUST NOT be reported as passed.

Proof source-scope admission MUST compare safely resolved repository-relative paths and reject the repository root and exact root `.git`, `.arrs` and `node_modules` trees, including normalized aliases and descendants, before configured command effects or evidence allocation/writes. Filesystem-identical case variants of the first root entry MUST also reject; distinct case-sensitive source entries MUST remain admissible. Possible case aliases MUST use non-following identity checks after path safety, without inspecting unrelated excluded roots. It MUST preserve supplied scope spellings and reject previously captured invalid alias proof through shared technical/accepted/review/work/audit validation. Legitimate source aliases and nested reserved-name source MUST remain admissible under the existing risk and safety gates.

Directory scope hashing MUST cover all files except exact repository-root `.git`, `.arrs` and `node_modules` trees. Nested directories sharing these basenames MUST remain covered. Excluded root entries MUST NOT be inspected to hash unrelated source, including when a dependency directory is symlinked; declared and visited source MUST retain symlink rejection. Generated architecture exclusions MUST NOT exclude files from declared proof scope hashes. Explicit file scopes hash their bytes. Traversal safety and file limits MUST remain enforced. Regenerate older proof when its formerly omitted source files now affect the scope hash.

Feature/docs proof uses `proof run --execute`; bug/refactor proof uses `proof start --execute` before editing and `proof finish --execute` after editing. `proof validate` MUST recheck the manifest and referenced evidence. Hashes establish local consistency, not authenticated execution or reviewer identity. Authors MUST make scope and residual risks honest; v0.1 does not independently prove full changed-file coverage.

Each bug/refactor finish MUST reserve a unique immutable attempt before command execution, preserve original baseline integrity and keep failed/interrupted history. Retry MUST use the original session, validate its baseline scenario against current configured argv and copy baseline log bytes/hashes unchanged into the new attempt. Finish MUST return an explicit manifest path for the chosen attempt; work/review references MUST identify that attempt. Interrupted capture without a completed manifest MUST NOT claim successful verification. Existing single-directory v0.1 manifests remain readable; new copied baseline evidence is self-contained, while provenance metadata is not authenticated lineage.

Proof plans and work items MAY supply `authorization.humanApproval` for required human permission before execution; legacy `review.humanApproval` remains its fallback. Independent implementation review MUST NOT be required before baseline capture. `status: "passed"` and `proof validate` indicate technical success and MAY support review readiness. `proof review <manifest> <input>` MUST attach an explicit implementation-stage record only after current successful canonical evidence validates, using exclusive append-only writes. The generated v0.1 `proof-review` record MUST bind proof ID, raw manifest SHA-256, exact scope hashes and a valid post-capture timestamp. It MUST preserve captured evidence. `proof validate --accepted`, completed work and audit proof-evidence MUST share current policy-required accepted validation. Review of another attempt or changed bytes/scope MUST NOT carry over. Legacy ambiguous plan review MUST remain readable but MUST NOT count as completed implementation review; required-review evidence needs an explicit attachment. Without configured review requirements, canonical technical evidence remains sufficient. This migration is local workflow enforcement, not authenticated reviewer attestation; see [ADR 0004](../adr/0004-proof-authorization-and-review.md).

## 7. Risk and autonomy

Read-only `proof explain` and `proof history` MUST reuse authoritative technical/accepted validation and preserve failed/interrupted attempts. Structured `proof-explanation` and `proof-history` diagnostics use version `0.1`. Provenance MUST remain an untrusted grouping hint. `proof report` MUST produce a new, ignored local static artifact strictly below `.arrs/reports/` outside canonical evidence, reject escaping/symlink paths before writes, escape all evidence markup and omit raw logs by default. Explicit bounded excerpts MUST verify original digests, label redaction/truncation and distinguish original from exported digests. These outputs MUST NOT execute configured commands, transfer acceptance, mutate canonical evidence or perform sharing/network actions. Audit MAY condense historical warnings while retaining individual paths/reasons and its authoritative accepted-evidence result. See [ADR 0006](../adr/0006-local-proof-explanations.md).

The reference ARRS checkout’s sensitive-path policy gives R3 floors to its execution configuration, shipped schemas and justified control implementation/runner/admission paths, with reasons recorded in [risk guidance](../risk.md). This is repository-specific coverage, not filename-specific classifier behavior or a default imposed on initialized consumers. Normalized overlapping scopes MUST retain configured floors in proof/work validation; unrelated documentation retains its existing floor and explicitly requested higher risk MUST remain higher.

The risk policy MUST define R0–R4, required checks, permitted autonomy and review/approval gates. Task risk MUST be at least the effective risk imposed by affected Feature Maps and sensitive paths and MUST be reassessed when scope changes.

| Risk | Impact                                                                                                  | Default policy                                                               |
| ---- | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| R0   | Negligible runtime risk: documentation/format/mechanical edits                                          | Bounded unattended execution; proportionate checks.                          |
| R1   | Isolated low-risk implementation                                                                        | Bounded unattended execution; checks/tests and applicable proof.             |
| R2   | Meaningful product/application behaviour                                                                | Review; checks/tests/behaviour and independent review.                       |
| R3   | Authentication, privacy, persistence, schema, public contracts or significant dependency/infrastructure | Human control, independent review and explicit approval.                     |
| R4   | Destructive, production, financial, secret-management or security-critical work                         | Human control; autonomous R4 implementation and deployment excluded in v0.1. |

R3/R4 MUST NOT permit unattended autonomy. R3 MUST require independent review and relevant check/test/verify commands. R4 MUST require human autonomy, human approval and independent review. Required local review records MUST be validated; protected external review systems SHOULD establish actual identity/independence.

Earned autonomy SHOULD be specific to a workflow/model, category, risk and demonstrated controls. A maturity level MUST NOT be interpreted as global agent trust.

### Explicit protected transition context

Candidate-only local evaluation MUST NOT be presented as authorization of changes to its governing configuration or policy. A caller MAY select a known-good external pre-change repository directory, independently retain its control digest before editing, and supply that selection to risk/proof/work/audit consumers. The selection MUST NOT be inferred from an arbitrary Git base or authenticated by candidate-authored plan text. A post-edit candidate-derived snapshot cannot satisfy this contract. The configuration filename remains `arrs.json`; configured policy and Feature Map locations remain consumer-defined.

Protected evaluation MUST validate and pin the selected configuration, risk policy, architecture policy and scanned Feature Map inventory, together with a bounded non-following source identity inventory of paths, types, devices and inodes. It MUST include directories/generated source and reject inventoried symlinks, excluding only the exact root metadata/evidence/dependency trees before inspection. Same-byte alias replacement MUST invalidate the selection; source preparation/build MUST precede digest selection and later source identity drift requires restoring the original immutable source. It MUST retain the maximum requested, baseline and candidate risk floor, both configurations' required checks, the stronger autonomy/review/human gates and earlier behavioral threshold. Required/planned command argv and effective timeout and applicable mapped targets MUST retain baseline bindings; this bounded implementation rejects binding drift before execution or allocation instead of executing multiple variants. Independently reviewed staged command transitions require newly selected known-good controls.

Proof/session/work/review records MAY carry optional `policyBaseline` root/digest fields. Bound records MUST require independently supplied matching context, never silently fall back to candidate-only admission, and preserve existing immutable attempt/review behavior. A candidate-only session MUST NOT acquire protected trust at finish, and unbound completed evidence MUST NOT be promoted through protected validation. Technical/accepted validation, work readiness/completion and audit MUST share these requirements; audit MUST validate supplied context and command drift before runtime effects. Selection and hashing are local assertions, not authenticated timing, reviewer identity, complete changed-file discovery or hostile-author attestation. See [ADR 0005](../adr/0005-trusted-pre-change-policy.md).

## 8. Objective maturity audit

Levels are cumulative: the achieved level is the highest L for which every control at levels 1 through L passes. Level 0 means level 1 is incomplete. Audit MUST report every control's identifier, level, pass/fail, detail and remediation, plus warnings. `--json` MUST return machine-readable output; `--require-level N` MUST fail when the achieved level is lower.

Qualification corrections retain serialized version `0.1` and the authoritative `passed` boolean. Diagnostic reports additionally expose `status` (`passed`, `failed`, `incomplete`, `blocked`, `not-evaluated`, `unsupported`) and audit may expose `dependsOn` prerequisite identifiers. Non-passed statuses MUST NOT unlock any level. These are additive output fields; consumers MUST tolerate new diagnostic fields. Empty architecture setup and optional local work configuration are additive schema acceptances, with no relaxation of capability requirements. Older CLIs cannot read optional `work`; use a corrected CLI when supplying it.

Default audit MUST perform no configured command execution. Consequently it can achieve at most level 1. `--execute` authorizes the runtime checks required for level 2 and above. Runtime success is observed for this audit; it does not guarantee future determinism or test quality.

| Level            | Control identifier         | Required observable capability                                                                                                          |
| ---------------- | -------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 1 Mapped         | `config`                   | Valid versioned config and safe repository paths.                                                                                       |
| 1                | `commands`                 | Configured mappings for check, test and build; mapped features also need verification targets.                                          |
| 1                | `knowledge`                | Substantive architecture, product and decision context.                                                                                 |
| 1                | `features`                 | Valid maps, existing references, owned boundaries and configured targets.                                                               |
| 2 Constrained    | `architecture`             | Actual declared-source import scan passes.                                                                                              |
| 2                | `architecture-guard`       | In-memory prohibited import into real source is rejected by the same scanner.                                                           |
| 2                | `security`                 | Heuristic security/control scan passes with valid scoped exceptions and dependency reasons.                                             |
| 2                | `check-executed`           | Explicitly executed configured check succeeds.                                                                                          |
| 3 Self-Verifying | `verification-executed`    | Explicitly executed test, build, verify and every mapped feature target succeed.                                                        |
| 3                | `proof-evidence`           | At least one current accepted proof validates with real logs, hashes, matching configuration and policy-required implementation review. |
| 4 Delegatable    | `risk`                     | Strict risk classes and actual sensitive-path rules are valid.                                                                          |
| 4                | `sensitive-classification` | Effective classification enforces configured sensitive-path floors.                                                                     |
| 4                | `context`                  | Concise agent instructions have relevant context pointers and durable operating rules.                                                  |
| 4                | `skills`                   | Installed ARRS pack has valid integrity and provenance.                                                                                 |
| 4                | `ci`                       | CI invokes check, test, verify and executed level 4 audit.                                                                              |
| 4                | `work-state`               | Valid self-contained work-item references and proof-aware transition support exist.                                                     |

Some controls use structural/textual heuristics, such as knowledge substance, instructions and CI invocation. Audit MUST disclose warnings and limitations; maintainers MUST NOT describe these as semantic proof. Level 4 supports delegation only for work allowed by the repository's risk policy.

The supported CI inspector is limited to configured GitHub Actions workflows with `push`, `pull_request` or `workflow_dispatch` triggers and bounded unconditional direct gate invocations. It MUST reject unestablished conditions, reusable workflows, disabled/failure-ignoring gates and unsupported syntax. Other valid GitHub trigger forms remain unsupported by this bounded adapter. Named npm gates MUST have existing scripts; CLI gates MUST use executable `run` forms. Static inspection MUST NOT claim a successful hosted run or protected admission controls. Doctor's CI and instruction presence checks MUST label that narrower claim accurately.

Before selecting semantic fields, the inspector MUST account for indentation ownership across workflow, job, step and nested block mapping/sequence boundaries. Scalar or inline values MUST NOT silently discard deeper descendants. Inconsistent indentation, mixed mapping/sequence entries and unconsumed descendants MUST fail capability with workflow location diagnostics. Empty values MAY own nested block mappings/sequences; supported literal blocks own opaque contents, so script text MUST NOT become YAML fields. The first nonempty literal content line, including a comment, MUST establish the minimum indentation for later nonempty contents. Leading blank lines MUST NOT exceed that indentation; later blank lines MAY. Dedented comments MAY follow a literal block before its next sibling, but later semantic descendants MUST NOT resume the terminated literal. This structural check does not expand the adapter to general YAML or GitHub Actions semantics.

Literal job identifiers MUST match `[A-Za-z_][A-Za-z0-9_-]*`. Supported `needs` forms are one literal identifier, an inline sequence of literal identifiers, or an indented block sequence without nested children. Empty `[]` means no dependencies. Single/double quoted identifiers and trailing comments MAY be used; unquoted YAML null/boolean values, expressions, aliases, anchors, tags, mappings, malformed sequences and scalar/sequence continuations MUST remain explicitly unsupported. Dependencies MUST reference declared jobs after all declarations are collected, allowing forward references. Missing dependencies, self-dependencies and cycles across any declared jobs, including disconnected auxiliary jobs, MUST fail capability. Cycle diagnostics MUST identify an actual cycle path rather than downstream jobs. This check remains bounded static inspection, not execution evidence.

Supported matrix dimensions MUST be nonempty literal arrays; dynamic/include/exclude forms remain unproven. Multicommand run steps require an explicit supported Ubuntu/macOS default runner; Windows, self-hosted or unresolved runners require separate direct command steps because failure propagation is not established for combined commands.

## 9. Work state and issue adapter

Work items MUST preserve structured risk, category, feature references, acceptance, context, verification, dependencies and decisions. State MUST distinguish `needs-triage`, `needs-information`, `ready-for-agent`, `in-progress`, `verification-failed`, `ready-for-review`, `human-required`, `completed` and `rejected`.

Readiness MUST require executable context and resolved dependencies/decisions. Review/completion MUST require valid proof matching task, risk and category and covering the current acceptance criteria and required verification targets; completion MUST enforce review/approval bound to the selected canonical proof attempt through the shared accepted validator. R4 MUST NOT become ready for autonomous agent execution. Transitions MUST be validated before local persistence. Repository-specific GitHub labels MAY map canonical states through `.agent/policies/work-labels.json`; risk and proof MUST NOT be hidden solely in labels. v0.1 supports the local model and mapping convention, with no remote issue mutation.

## 10. Skills and upstream evolution

Installed-pack assessment through skills testing, doctor and audit MUST use one authoritative semantic validator. Reconciliation candidates MUST pass the same strict metadata, document, source-provenance and exact pinned MIT license contract before writes. Nonempty required terms and vendor-neutral invocation MUST remain enforced even when document hashes are refreshed. Installed reconciled versions MUST be assessed against their own pins. Full staged source byte/inventory verification remains a workflow responsibility; core MUST NOT depend on workflows.

Selected engineering skills MUST implement ARRS context discovery, risk, boundaries, checks, behavioural proof and handoff requirements as applicable. A skill SHOULD represent a reusable workflow rather than duplicate mechanically enforced rules. Skill authoring and integration are specified in [skills](../skills.md).

The skill pack MUST record the examined upstream repository, pinned revision, license, date/version and explicit dispositions for engineering source skills: `ADOPT`, `ADAPT`, `WRAP`, `REPLACE` or `EXCLUDE`. Materially derived skills MUST retain source provenance, adaptation version and major changes without loading all provenance on every invocation. Required license attribution MUST be preserved.

Installed skills MUST remain usable offline. Status/diff/sync MUST distinguish pristine upstream, derived pack and local installed content. Upstream fetching MUST be explicit. Synchronization MUST stage rather than overwrite ARRS adaptations. Reconciliation MUST be deliberate, update provenance and test the pack; it MUST preserve unacknowledged local edits.

## 11. Gardener and metrics

Gardener candidates MUST separate observation, evidence, recommended enforcement and proposed change. The workflow SHOULD investigate drift, repeated mistakes, stale maps, weak/flaky verification, workarounds, dependency creep and instruction bloat. It MUST avoid uncontrolled automatic rewrites. Mechanical prevention SHOULD take precedence over another instruction when practical.

Metrics MUST be versioned and local by default. Existing manual 0.1 events retain their explicit false/zero semantics and recorded-event denominators. Separate 0.2 outcomes MAY record lifecycle facts automatically at their owning proof/work boundaries and explicit append-only follow-up observations. Each metric MUST retain known/unknown counts and use its known denominator; empty denominators MUST return null. Exact observation windows and comparable workflow/risk/control cohorts MUST remain visible. Stable duplicate source identities MUST NOT inflate task/attempt counts; interrupted allocation MUST NOT establish success. Collection MUST NOT change readiness, risk, approval or permitted autonomy. See [metrics](../metrics.md) for persistence/recovery, limits and privacy. They SHOULD capture first-pass verification, intervention, rejection, reverts, escaped defects, architecture failures, repeated failure categories, verification completeness, scope, risk and workflow/model identity where known. PR volume MUST NOT be a trust metric. Missing data MUST NOT be invented. Sensitive data SHOULD be excluded or pseudonymized before recording or sharing.

## 12. Evolution and exclusions

An optional local stdio MCP adapter MAY expose shared read-only task preparation, proof/history, doctor and unevaluated audit through strict version-0.1 `mcp-inspection` results. Launch-selected root/baseline context MUST NOT be replaced by tool arguments; configured commands, writes and acceptance MUST NOT be available. Default results MUST omit source/document contents and raw logs. Explicit context remains untrusted data. Bounded pages MUST retain all navigable values or fail explicitly; continuation MUST reject expiry, selector mismatch and relevant source/configuration/result drift. Protocol compatibility MUST name the actual tested client/version. See [local MCP](../mcp.md) for the `2025-11-25` stdio contract, privacy and limits.

Serialized contracts MUST fail on unsupported versions. A future release SHOULD provide explicit migrations when changing meanings or required fields; v0.1 has no automatic forward migration. Skill adaptation versions evolve separately with provenance and compatibility tests.

v0.1 excludes production deployment, autonomous R4 changes, a hosted backlog/SaaS, model training, mandatory orchestration vendors, universal language coverage and a graphical UI. Conformance does not certify security, authenticate local proof or establish arbitrary test correctness.

## Optional explicit-changeset capability

A v0.1 Proof Plan MAY negotiate `changeset: {version: "1", mode: "git", base: "<explicit local revision>"}`. This is an additive capability, not reinterpretation of existing evidence. A captured manifest MUST contain the corresponding complete version-1 `changesetSnapshot`; validation MUST recollect and compare its explicit base/HEAD, repository/worktree identity, index and bounded working inventory. Unknown capability versions fail. Manual scope inspection MUST remain declared-only.

Complete changeset coverage MUST include committed, staged, raw-byte unstaged and nonignored untracked changes, preserving layers and both rename endpoints. Deleted regular source MUST retain its base object/mode and explicit absence; only a complete captured snapshot permits a domain-separated absence scope digest. Current/historical mapped obligations and sensitive floors MUST not disappear on deletion/rename. Git comparison controls MUST NOT substitute for trusted independently selected pre-change policy context. Existing immutable attempts, authorization, completed implementation review, protected baseline requirements and local-integrity limitations continue to apply.

The qualified bounded adapter uses Git 2.52.x, disables helpers, optional writes, lazy fetching and transport, and rejects missing objects, unsafe paths, unsupported types/index states, exceeded limits or concurrent drift. Root metadata/evidence/dependencies are explicitly excluded; tracked excluded changes remain visible. Read-only collection MUST NOT execute project commands or mutate source, index, evidence, configuration or work state. See ADR 0006 for bounds, endpoint semantics and compatibility.

## 13. Guided capability adoption

`adopt plan <input> [--output <directory>]` authors one capability using separate strict version 0.1 adoption-input/proposal documents; existing contract schema meanings are unchanged. Default planning MUST perform no writes, application-script execution, installation or network requests. Supplied acceptance/ownership/paths/verification MUST remain distinguishable from sourced discovery candidates. Unsupported architecture, missing facts, ambiguous scripts and conflicting controls MUST produce actionable blockers rather than invented content or readiness. Deterministic proposals MUST include ordered checklist/blockers, input snapshots and operations with path, reason, exact original absence/bytes/mode/digest and replacement bytes/mode/digest. Optional exports MUST use fresh canonical contained ignored `.arrs/adoption/` storage outside proof evidence.

`adopt apply <proposal>` MUST reject unsupported versions/flags, malformed proposals, unresolved blockers, repeated/unsafe targets and stale originals/input snapshots before effects. It MUST rederive the deterministic patch, preserve unrelated bytes and existing modes, and execute no proposed commands. Existing control integration MUST append explicit declarations only, retain pre-change controls and require independently supplied baseline context plus a separate actual execution-authorization input bound to exact proposal bytes. Proposed policy/approval-looking fields MUST NOT authorize themselves. R4 application remains human-owned. Ordinary failure MUST report rollback/partial-write state and retain original bytes/modes before mutations. Crash recovery MUST remain reviewable and preserve intervening changes; no cross-process transaction is claimed.

Successful application MUST report configured capability and remaining checks, with behavioral proof unevaluated and acceptance false. It MUST NOT create proof, dependency acceptance, hosted CI observations or maturity credit. The [adoption decision](../adr/0006-guided-adoption.md) specifies compatibility, preservation, privacy and recovery.

## 14. Opt-in receipt version 1

Receipt schema version 1 is separate from existing proof version 0.1. Strict kinds `receipt`, `receipt-statement`, `receipt-policy`, `receipt-context`, `receipt-run`, `receipt-review` and `receipt-bundle` define a bounded Ed25519 DSSE/in-toto offline provider contract. Unsupported versions/providers fail explicitly. Existing proof/session/review parsing and acceptance remain unchanged; local exports reuse canonical technical validation and never upgrade local integrity to authenticated execution. The selected GitHub offline profile requires external pinned consumer policy/context, separately authenticated provider/review inputs, immutable Git candidate/base and retained controls, actual command/log digest observations, criterion links and exact completed review binding. Successful conformance still returns `admission: false` and unqualified hosted assurance. Export/import stays metadata-only, bounded, ignored, contained and exclusive.

# Security controls and limitations

Repository commands are executable code. Review configuration and scripts before enabling `audit --execute`, proof execution, setup or any command from an unfamiliar repository. `shell: false` prevents implicit shell interpretation; it is not a sandbox. An explicitly configured interpreter, package install script or executable can still run arbitrary code with the caller's privileges.

v0.1 checks a defined set of secret and unsafe-shortcut patterns, architectural imports, configured control exceptions and risk/proof requirements. Text scanning includes root and nested `.env`, `.env.local`, `.env.production` and compound dotenv suffix variants, including files ignored by Git, alongside supported source extensions. The 2 MB text bound and deliberate generated-directory discovery exclusions remain enforced; secret findings cannot be waived. These controls can miss unfamiliar credential formats, runtime behaviour, malicious code and dependencies. A passing audit does not establish secure software.

Keep credentials in the stack's supported secret store or ignored local environment. Never put them in committed source, maps, work items, metrics or captured command output. Proof logs can contain command output; inspect and redact sensitive material before sharing evidence. Initialization creates a missing `.arrs/.gitignore` (`*` with `!.gitignore`) without replacing existing root or scoped ignore files. A literal root `.arrs/` rule does not establish effective protection when later rules negate it. Existing unsafe conventions remain preserved and produce actionable requirements.

Proof and review writes check the whole configured evidence directory strictly below repository-root `.arrs/`, using its normalized path without a trailing slash. In a Git worktree—including a containing worktree—bounded `git check-ignore --no-index --quiet` must confirm exclusion of that existing directory or an existing ancestor. Git treats absent paths as files, so a prospective directory with no confirmed ignored ancestor requires the canonical scoped marker even when Git is available. Directory-only negations cannot be safely tested against a missing path. File-only rules may be rejected by this conservative subtree policy. Unignored directories, symlink/unsafe paths and operational Git failures stop capture before command effects or evidence allocation. Protection is checked again before logs/session/manifest/review writes; changing ignores during configured execution prevents unprotected output writes. Current proof validation also checks protection.

When Git is absent, there is no Git worktree, or a prospective directory has no confirmed ignored ancestor, only a scoped `.arrs/.gitignore` containing a literal `*` or `/*`, optional `!.gitignore`, empty lines and comments starting with `#` qualifies. Indented patterns, other negations and arbitrary root ignore grammar are unsupported in this fallback. Capture and review output reports `ignoreProtection.method` as `git` or `scoped-marker` with its limits: the latter establishes a bounded local convention and does **not** claim measured Git state. Initialization still works without Git. Repair a preserved marker deliberately or initialize Git with an effective whole-directory rule before proof.

For a fresh checkout or CI job, run `arrs init` after installing/building the CLI and before proof capture. The scoped marker is generated locally and is not tracked under the checkout's ignored `.arrs/` tree. A root directory-only ignore rule alone cannot establish the conservative convention for a prospective directory. The reference workflow initializes before its unchanged proof and executed audit gates; initialization preserves existing configuration and source.

Ignore rules do not remove already tracked files, prevent access or serve as secret storage. Inspect existing tracking and sensitive logs separately before sharing. The `--no-index` query checks ignore rules independently of the index.

Dependency additions belong in review with a reason, scope and lockfile change. The configured exceptions document records dependency names and reasons; v0.1 checks npm production, development and optional dependency declarations against those records. Remote code execution and install hooks require explicit examination under the applicable risk policy.

Compiler/lint suppressions and remote-execution exceptions require the exact path, rule, matching text, reason, expiry date and approver. Expired or missing-path exceptions fail the gate. A blanket match undermines the intended scope; reviewers must assess substantive justification. Secret findings cannot be waived through this mechanism.

Changes to authentication, persistent data, privacy, public contracts or infrastructure raise risk. Destructive and production operations require human-controlled execution and stack-specific safeguards. ARRS v0.1 does not automate R4 implementation or production deployment.

Use the target stack's normal secure engineering practices for external input, authorization and dependency review. Establish independently protected CI and review permissions if the threat model includes an author attempting to weaken controls or forge proof.
